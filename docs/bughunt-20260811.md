# Bug Hunt — 2026-08-11

Scheduled sweep for real bugs across the repository (not style nits): the
Python MSQ scaffolding (`tools/msq_*.py`, `tools/bin_harness_384.py`), its
test suite, the JSON schemas, and the four operator-facing shell scripts.

## Method

The Python side was read end to end and exercised: `python3 -m pytest tests
-q` (40/40 passing before and after), `python3 -m compileall -q .`, and a
manual run of `tools/msq_demo_run.py` across several sessions to check the
personalization-warmup and guardrail-clamping paths by hand. No defect was
found there — it has already been through several audit rounds (see
`docs/dormant-components-audit.md`) and it shows.

The four shell scripts (`cli-validation.sh`, `ai-task-prioritization.sh`,
`multi-host-deployment.sh`) and `tools/add_line_numbers.py` were audited for
the class of issue `REVIEW.md` previously flagged repo-wide (`set -e`
without `-u`/`pipefail`, unquoted/unescaped interpolation). Each finding
below was reproduced against the pre-fix code before being fixed.

## Findings and fixes

### 1. `cli-validation.sh` — a missing required tool aborted the entire validator

`validate_required_tools()` called `check_command "<tool>" true` as a bare
statement. `check_command` returns `1` when a required tool is missing.
Under the script's `set -e`, a bare (non-conditional) command returning
non-zero aborts the whole script immediately — so on a host missing e.g.
`curl`, the script died right there, before `validate_optional_tools`,
`validate_file_permissions`, `validate_directory_structure`,
`validate_configuration_files`, `validate_git_configuration`,
`validate_shell_scripts_syntax`, the audit log, or the summary ever ran. A
tool whose entire job is to enumerate every problem instead silently
reported only the first one and stopped.

Reproduced by running the script with a `PATH` containing every required
tool except `curl`: before the fix it printed 8 checks and exited after
`curl is not installed (REQUIRED)`; after the fix it runs all 39 checks to
completion and still exits non-zero.

**Fix:** append `|| true` to each required-tool `check_command` call, so a
missing tool is recorded (via `log_error`, which already increments
`FAILED_CHECKS`) without tripping `errexit`.

### 2. Unescaped values embedded in JSON heredocs produced invalid JSON

- `ai-task-prioritization.sh`: `prioritize_task` wrote `task_id`/`task_name`
  (arbitrary caller-supplied strings) straight into a JSON heredoc. A task
  name containing a `"` — e.g. `Fix "urgent" bug` — broke the JSON, which
  then breaks `summarize_recent_tasks`'s `jq -s` parse of that log file.
- `multi-host-deployment.sh`: `create_audit_log` did the same with the
  `environment` argument.

Reproduced: `./ai-task-prioritization.sh TASK-1 'Fix "urgent" bug' 9 10 3 1
9` wrote a log file that `json.load()` rejected with
`JSONDecodeError: Expecting ',' delimiter`.

**Fix:** added a small `json_escape()` helper (escapes `\`, `"`, and
newline/tab/carriage-return) to both scripts and routed the interpolated
values through it before embedding them in the heredoc.

### 3. Audit-log filenames could collide within the same second

All three scripts derived their audit-log filename from
`date -u +%Y%m%d-%H%M%S` alone (1-second resolution, no per-process
component). Two invocations inside the same second — overlapping CI jobs, a
caller looping over several tasks quickly — would compute the identical
filename. `cli-validation.sh` and `multi-host-deployment.sh` open it with
`cat >` (truncate), so the loser's log silently vanishes;
`ai-task-prioritization.sh` opens it with `cat >>` (append), so concurrent
writes can interleave into a corrupt JSON object.

**Fix:** appended `$$` (the script's own PID) to each audit-log filename.
`ai-task-prioritization.sh`'s log-listing glob (`task-prioritization-*.json`)
and its lexicographic sort still work correctly, since the PID is a suffix
after the timestamp component that sorting keys on.

### 4. `tools/add_line_numbers.py` — one non-UTF-8 document crashed the whole batch

`write_numbered_copy` and `number_in_place` called `path.read_text(encoding
="utf-8")` with no error handling. A single non-UTF-8 file among the
scanned `.md`/`.txt`/`.rst`/etc. documents (not uncommon with older
Windows-1252 text) raised `UnicodeDecodeError` and killed `main()` before it
printed any summary or processed the remaining files — unlike every other
per-file skip path in the script (`already_numbered`, missing extensions,
excluded directories), which degrade gracefully.

Reproduced with a two-file input directory (one valid UTF-8 doc, one with an
invalid continuation byte): before the fix, the run crashed with a
traceback and processed neither file; after the fix, it prints `Skipping
non-UTF-8 file: ...` and still numbers the valid file.

**Fix:** wrapped both read sites in `try/except UnicodeDecodeError`,
logging and skipping the offending file instead of aborting.

## Verification

After all fixes: `bash -n` on all four scripts, `python3 -m compileall -q
.`, and `python3 -m pytest tests -q` (40 passed) all still pass, plus the
manual reproductions above for each fix.

## Not changed

- `ai-task-prioritization.sh`'s `calculate_priority_score` does not validate
  that `urgency`/`impact`/`effort`/`dependencies`/`risk` are numeric before
  handing them to `bc`; a non-numeric argument computes a silently wrong
  score rather than erroring, because `bc` treats an unrecognized token as a
  zero-valued variable. Left as a follow-up: `summarize_recent_tasks`
  already has a validation precedent (`limit` is regex-checked) that a
  future change could mirror for the five scoring inputs.
- The `shell-script-debug` job in
  `.github/workflows/shell-script-ci.yml` runs every executable `.sh` file
  with no arguments (and `--help` if detected) as part of CI. This is
  pre-existing CI behavior, not part of this sweep's scope, and touching it
  risks unintended side effects in the deployment/prioritization scripts
  during CI runs.
